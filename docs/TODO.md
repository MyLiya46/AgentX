# Agent项目开发计划 - Todo List

## 已知 Bug

- [ ] **Agent聊天框上传文件后前端显示文件名被重命名，非用户原始文件名**
  - 位置: 前端文件上传组件 → 消息展示组件
  - 现象: 用户在Agent对话中上传文件并发送消息后，前端聊天界面显示的文件名被重命名为统一格式（如 `file.pdf`、`file.jpg`），而非用户本地的原始文件名（如 `产品需求文档.pdf`、`会议截图.png`）
  - 影响: 用户无法通过文件名快速识别上传的是哪个文件，体验较差
  - 待决策:
    - **方案A（推荐）**: 保留用户原始文件名 — 前端上传时携带原始文件名，后端存储并返回，前端展示原始文件名。更符合用户直觉
    - **方案B**: 统一命名 — 使用 `{uuid}.{ext}` 格式，仅在下载时还原。安全性更好但用户体验差
    - 需同时考虑: 文件名安全过滤（防XSS/路径遍历）、中文文件名编码、重名文件处理策略
  - 修复方向:
    1. 定位文件名在哪个环节被替换（前端上传组件 / OSS上传逻辑 / 后端消息存储 / 前端消息渲染）
    2. 决定命名策略后统一修改各环节
    3. 添加文件名安全过滤工具方法

- [ ] **Agent聊天框上传图片后前端显示 file.jpg 且图片加载失败，但Agent已能感知图片内容**
  - 位置: 前端图片消息渲染组件
  - 现象: 用户在Agent对话中上传图片文件，前端聊天界面中：
    - 文件名统一显示为 `file.jpg`（非原始文件名，与上一条问题相关）
    - 图片缩略图/预览显示"图片加载失败"
    - 但后端已成功解析图片内容，Agent回复中能正确描述图片内容 → 说明OSS上传和内容下载链路正常，问题出在前端图片展示逻辑
  - 根因推测: 前端图片消息组件使用的图片URL可能有误（可能用了错误的OSS地址、缺少认证参数、或URL拼接方式不对），导致 `<img>` 标签加载失败
  - 修复方向:
    1. 排查前端图片消息组件中 `src` 属性的值是否与OSS实际可访问URL一致
    2. 检查OSS Bucket公共读权限或签名URL生成逻辑
    3. 修复后确保图片预览正常显示，且保留原始文件名

- [ ] **Agent聊天框支持的文件类型有限，暂不支持 .doc/.docx/.pdf 等文档格式**
  - 位置: 后端文件内容解析模块（`AbstractMessageHandler` 文件类型判断逻辑）
  - 现象: 当前Agent聊天上传文件仅支持 txt、md、图片等基础格式，不支持 Word 文档（.doc/.docx）的内容解析
  - 影响: 用户无法在对话中直接上传和解析 Word 文档，需手动转换为纯文本后再上传
  - 修复方向:
    1. 引入 Apache POI 或类似的 Java Word 文档解析库
    2. 扩展 `downloadTextFile()` / 文件类型判断逻辑，增加 `.docx`、`.doc` 到支持列表
    3. 实现 Word 文档内容提取为纯文本的工具方法（提取段落文字，忽略复杂格式）
    4. 考虑是否需要同时支持 PDF 解析（一并评估）

- [ ] **Agent聊天框上传文件后Agent无感知（文件URL已到达后端但内容下载失败）**
  - 位置: `AbstractMessageHandler.downloadTextFile()` → `convertFileUrlsToContents()` → `buildHistoryMessage()`
  - 现象: 用户在Agent聊天框上传txt文件，OSS上传成功，前端将fileUrls随消息发送到后端，但Agent回复中完全未提及文件内容
  - 根因: `downloadTextFile()`使用`HttpURLConnection`直连OSS公网URL下载文件，下载失败时静默返回null，`convertFileUrlsToContents()`收到null后跳过该文件，`buildHistoryMessage()`不为文件创建UserMessage → Agent对文件无感知。全程无用户提示
  - 待排查: OSS下载失败的具体原因（403权限/网络不通/DNS等），需要先让错误可见
  - 修复方向:
    1. 修复静默失败：下载失败时通过SSE向用户发送提示，同时升级日志级别
    2. 修复`ChatRequest.message`的`@NotBlank`校验与前端不一致（前端允许仅文件无文本）
    3. 修复临时消息实体null ID污染问题（`ConversationAppService.setupContextAndHistory()`）
    4. 引入Redis缓存文件内容，避免每次对话重复下载
    5. 长期优化：考虑使用OSS SDK + AccessKey认证下载，替代无认证的HttpURLConnection
  - 相关文件:
    - `AbstractMessageHandler.java:616-653` (downloadTextFile)
    - `AbstractMessageHandler.java:565-598` (convertFileUrlsToContents)
    - `AbstractMessageHandler.java:511-561` (buildHistoryMessage)
    - `ConversationAppService.java:344-350` (临时消息实体)
    - `ChatRequest.java:12` (@NotBlank校验)

- [ ] **RAG文件处理强制要求OCR模型配置，即使TXT/MD不需要**
  - 位置: `RagQaDatasetAppService.autoStartPreprocessing()` + `UserModelConfigResolver.getUserOcrModelConfig()`
  - 现象: TXT/MD 文件上传后卡在 `processing_status=0`，因为 `autoStartPreprocessing` 在判断文件类型之前就强制获取 OCR 模型配置，用户未配则抛异常 → 状态重置为 0
  - 根因: `TXTRagDocDocumentProcessing` / `MarkdownRagDocumentProcessing` 实际上只用 `TextDocumentParser` 做纯文本解析，根本不需要 OCR 模型。但 `autoStartPreprocessing` 不管文件类型，都先调 `getUserOcrModelConfig()`，导致纯文本文件也被阻塞
  - 修复方向: `autoStartPreprocessing` 应根据文件扩展名判断是否需要 OCR 模型，txt/md/csv 等纯文本格式应跳过 OCR 配置获取
  - 临时绕过: 在用户设置中配置 `defaultOcrModel`（复用 chat 模型 ID 即可）
